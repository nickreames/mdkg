# mdkg 0.6.0 qualification draft

Status: **UNPUBLISHED / NOT QUALIFIED**. Maintainer working draft, not a release
announcement or approval to migrate a project. The target is direct 0.6.0 after
qualification. Package metadata and the public release manifest still identify
0.5.2; intermediate audit packages can therefore also report 0.5.2. Identify
audit candidates by their recorded source and artifact hashes, not version alone.

This document does not change any compatibility policy. Unresolved decisions
below must be accepted and implemented before their guidance becomes final.

## Intended release outcome

Make Git-native project memory easier to enter and safer for separate developer
branches: compact default initialization, focused instruction discovery, stable
graph/node identities behind readable aliases, and explicit reviewed semantic
reconciliation. A single-writer main-branch workflow remains supported. This is
not distributed scheduling, simultaneous checkout writing, or automatic Git merge.

## Getting started with the qualified candidate

These instructions describe candidate behavior, not published 0.5.2 behavior.
Do not copy them into published-version instructions without that distinction.

1. Check the installed version and, during qualification, its artifact receipt.
   The supported runtime minimum is Node 24.15.0; final evidence must also cover
   the available Node 24 line and the specified Node 26 compatibility runtime.
2. In a new owned project, run `mdkg init`. Compact agent setup is the default.
   Use `mdkg init --graph-only` to omit agent guidance. `mdkg init --agent`
   remains a compatibility spelling; do not combine it with `--graph-only`.
3. Read one root entrypoint, `AGENTS.md` or `CLAUDE.md`. Its managed section
   routes to `.mdkg/AGENT_START.md`; detailed generated guidance stays under
   `.mdkg`. User-authored root content and project README/LICENSE remain owned
   by the project, not disposable generated output.
4. Run `mdkg index`, then `mdkg validate --json`. Initialization creates source
   scaffold files; indexing creates rebuildable access caches. Do not mistake
   missing fresh caches for an instruction to rewrite project memory.
5. Discover relevant work and skills with `mdkg search`, `mdkg show`, and
   `mdkg skill list/search/show`. Use `mdkg help` for command discovery and a
   concise pack when transferring task context. No universal handbook reread is
   required for every task.

The slash-separated skill names above describe a command family, not one shell
command. Current exact flags are in [the command matrix](../CLI_COMMAND_MATRIX.md).

## Upgrading an existing scaffold

Scaffold upgrade and graph-format migration are separate operations. Neither
implicitly grants implementation, Git, release, or deployment authority.

- `mdkg upgrade --json` previews owned changes without writing. Review the
  preserved customizations, blocking conflicts, and exact proposed paths.
- Use a bounded `--only` selection when appropriate; required derived mirrors
  remain part of the reviewed plan. It is not permission to ignore conflicts.
- Application requires the exact reviewed `--plan-hash`. Any changed source,
  selected input, or dependency requires another preview rather than reuse of
  stale approval. Do not use initialization with force as an upgrade shortcut.
- Interrupted upgrade resume/recovery requires its journal-bound hash and
  refuses subsequent user edits. Preserve those edits and resolve the refusal;
  never overwrite them just to complete a scaffold refresh.
- Canonical skills live under `.mdkg/skills`; native mirrors are projections.
  Resource links and mirror bytes must remain valid after upgrade.

## Separate developer branches

### Identity before integration

Version 2 adoption is explicit. Keep legacy graphs usable without silently
inventing identities on read or during indexing. For migration, preview with
the reviewed graph UUID, origin UUID, and a local Git ancestor. A shared graph
namespace identifies the same project; independent branch additions need
distinct origins. Branch-local nodes are full authored nodes, usable before
commit, not a separate reduced-function draft namespace.

Migration examines history and may require explicit continuity decisions.
Restore-ancestor versus new-identity choices need the exact review hash and a
reason. Unknown, shallow, ambiguous, or incomplete ancestry must not be repaired
by guessing. Historical prose and immutable external evidence are not rewritten
merely because today's numeric alias changes.

### Reviewed reconciliation

1. Preserve the target checkout's staged and unstaged work. Establish the exact
   local ancestor, incoming commit, and current target HEAD.
2. Preview `mdkg graph reconcile` with those refs. Read the identity mapping,
   changed paths, conflicts, and evidence before applying anything.
3. Different identities sharing an alias are not two edits of one node: keep
   target aliases and review deterministic incoming remaps and reference binds.
   Same-identity conflicting edits, evidence/lifecycle changes, deletion, and
   reintroduction need explicit choices rather than duplicate-ID repair.
4. Supply reasoned decisions, preview again, and apply only the resulting exact
   unchanged plan hash. Repeated integration must use recorded target acceptance,
   not trust an imported receipt merely because its self-hash verifies.
5. Validate graph identities/references and review the authored diff. Commit or
   Git integration remains a separate user workflow; reconciliation does not
   stage files, switch branches, merge Git history, fetch, or push.

Clone preserves same-project identity. An independent fork creates new graph
and node identities with lineage mappings. Neither transfers live writer locks,
local selection, or runtime ownership. Parent graphs may inspect authorized
child snapshots; they do not acquire child write authority or a promise that
the snapshot reflects the child's current working tree.

## Recovery and compatibility gates still unresolved

These are release blockers, not accepted user workarounds:

| Gate | Observed condition | Proposed direction, not yet accepted |
| --- | --- | --- |
| Old writers on v2 | Published 0.5.2 can partially write before rejection; old initialization can bypass a proposed configuration fence | Require every writer to upgrade, add the available capability fence, document remaining old-client limits |
| Killed writer | Abrupt termination can leave a lock; ordinary recovery then refuses or times out | Explicit reviewed lock-and-journal-bound recovery; refuse live or ambiguous ownership, never infer abandonment from age |
| Legacy public bundles | Config-less snapshots cannot prove arbitrary configured runtime exclusions | Preserve inspection, require fresh safe export before materialization |
| Observational Git reads | Some inspection paths refresh parent/child Git index metadata | Fix every proven helper, preserve staged entries and exact index bytes, then repeat installed and mounted-graph qualification |
| Historical migration | Some historical evidence cannot be given an unambiguous identity automatically | Keep precise unsupported-condition evidence; do not invent identities or edit canonical history to pass |

For a supported caught-error transaction, `mdkg graph recover` can inspect the
journal before a reviewed resume or rollback. That existing capability is not
proof that killed-writer lock recovery is solved. Do not manually delete an
unexamined lock, weaken custody checks, or restore a whole checkout to bypass it.

## Candidate change-note inventory

This is a source-grounded draft inventory, not the final complete changelog.
Refresh it against the exact final package inputs after remediation.

- Compact default bootstrap, root managed sections, focused skill discovery,
  self-contained public seed guidance, preview-hash upgrades and edit-preserving
  recovery.
- Explicit versioned graph identity, ancestor-grounded migration, branch-local
  authoring, reviewed alias/reference reconciliation, and durable lineage and
  target acceptance evidence.
- Identity preservation through formatting, packs, scaffold upgrades, template
  import and graph transport; portable dependency labels remain valid without
  fabricating node identities.
- Clock-independent SQLite source fingerprints, observational graph/cache
  reads, complete piped CLI output, and measured duplicate-path-check reduction.
  The remaining Git-index metadata defect is not included as fixed.
- Containment and bounded-input fixes for derived caches, graph discovery,
  pack output, archive verification, event history, template discovery, guidance,
  subgraph bundles and skill resources. Do not claim universal filesystem-race
  immunity or final security clearance from these local fixes.
- Nested workspace export ownership and partial transport-state remediation.
  Public omission of private DB payloads must be verified across all consumers;
  the config-less bundle policy is still open.
- Complete ordinary test-family discovery, installed-package runtime fixtures,
  generated CLI/docs parity, package provenance and manifest-backed release gates.
  Website/demo build-cache and release-display changes are repository consumer
  surfaces, not additional npm runtime capabilities.

Full operational receipts, accounting, reputation, scheduling, and provider
state remain consumer-owned. mdkg carries distilled intent, portable contracts,
accepted project evidence and explicit references. This release does not add
federation, remote skill distribution, or autonomous self-improvement.

## Final qualification and publication handoff

Before changing this draft to release guidance:

1. Finish all blocker fixes and accepted compatibility/recovery policies.
2. Set package/lock metadata to 0.6.0, prepare complete CHANGELOG notes, and set
   the matching public release manifest to `draft`, never `published` in this
   local-only pass. Generate and verify release/command-reference projections.
3. Review the exact remediation range independently for security. Preserve
   canonical scan reports in their designated private location; commit sanitized
   findings, dispositions and report hashes only.
4. Run all six installed fixture families across the required runtimes. Include
   actual read-only mounts, legacy/v2, JSON/SQLite, private migration rehearsal,
   independent branches, mixed staged/unstaged state, recovery, scale and goals.
   A known refusal can be accepted only against an explicit agreed contract.
5. Run the full release ladder with coverage floors unchanged: 89% lines,
   77% branches, 96% functions. Verify CLI/docs/skills/package contents, graph
   full/changed-only checks, SQLite, diff review, and protected-state bookends.
6. Seal one tarball with its integrity, file manifest, package-input hashes,
   source revision, runtimes, audit reports and validation receipts. Package-input
   changes invalidate the seal. Evidence-only commits may follow without changing
   the sealed package bytes.
7. Leave publication paused. A future authorized publication pass must recheck
   blockers and consume the exact qualified artifact. A green goal status alone
   is not publication evidence or authority. Push, tag, release and provider
   actions retain their separate authority boundaries.

Until those gates close, report **NOT_READY**, not “ready except for publishing.”
