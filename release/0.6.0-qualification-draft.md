# mdkg 0.6.0 qualification draft

Status: **UNPUBLISHED / NOT QUALIFIED**. Maintainer working draft, not a release
announcement or approval to migrate a project. The target is direct 0.6.0 after
qualification. Package/lock metadata now identify 0.6.0 and the matching public
release manifest is `draft`. This does not publish or deploy anything. Earlier
intermediate audit packages report 0.5.2; identify every candidate by its source
and artifact hashes, not version alone. The changelog date records preparation,
not an assertion of a registry publication date.

Decisions94-96 are accepted. The implementation prerequisites are locally
verified, but final-artifact/platform/security qualification remains open. Broader
documentation audit and polish are deferred; this guide covers release-critical
behavior, breaking changes and honest qualification limits. Windows is unqualified.

## Intended release outcome

Make Git-native project memory easier to enter and safer for separate developer
branches: compact default initialization, focused instruction discovery, stable
graph/node identities behind readable aliases, and explicit reviewed semantic
reconciliation. A single-writer main-branch workflow remains supported. This is
not distributed scheduling, simultaneous checkout writing, or automatic Git merge.

## Getting started with the qualified candidate

These instructions describe candidate behavior, not published 0.5.2 behavior.
Do not copy them into published-version instructions without that distinction.

1. Check the installed version and, during qualification, its artifact receipt.
   The supported runtime minimum is Node 24.15.0; final evidence must also cover
   the available Node 24 line and the specified Node 26 compatibility runtime.
2. In a new owned project, run `mdkg init`. Compact agent setup is the default.
   Use `mdkg init --graph-only` to omit agent guidance. `mdkg init --agent`
   remains a compatibility spelling; do not combine it with `--graph-only`.
3. Read one root entrypoint, `AGENTS.md` or `CLAUDE.md`. Its managed section
   routes to `.mdkg/AGENT_START.md`; detailed generated guidance stays under
   `.mdkg`. User-authored root content and project README/LICENSE remain owned
   by the project, not disposable generated output.
4. Run `mdkg index`, then `mdkg validate --json`. Initialization creates source
   scaffold files; indexing creates rebuildable access caches. Do not mistake
   missing fresh caches for an instruction to rewrite project memory.
5. Discover relevant work and skills with `mdkg search`, `mdkg show`, and
   `mdkg skill list/search/show`. Use `mdkg help` for command discovery and a
   concise pack when transferring task context. No universal handbook reread is
   required for every task.

The slash-separated skill names above describe a command family, not one shell
command. Current exact flags are in [the command matrix](../CLI_COMMAND_MATRIX.md).

## Upgrading an existing scaffold

Scaffold upgrade and graph-format migration are separate operations. Neither
implicitly grants implementation, Git, release, or deployment authority.

- `mdkg upgrade --json` previews owned changes without writing. Review the
  preserved customizations, blocking conflicts, and exact proposed paths.
- Use a bounded `--only` selection when appropriate; required derived mirrors
  remain part of the reviewed plan. It is not permission to ignore conflicts.
- Application requires the exact reviewed `--plan-hash`. Any changed source,
  selected input, or dependency requires another preview rather than reuse of
  stale approval. Do not use initialization with force as an upgrade shortcut.
- Interrupted upgrade resume/recovery requires its journal-bound hash and
  refuses subsequent user edits. Preserve those edits and resolve the refusal;
  never overwrite them just to complete a scaffold refresh.
- Canonical skills live under `.mdkg/skills`; native mirrors are projections.
  Resource links and mirror bytes must remain valid after upgrade.

## Separate developer branches

### Identity before integration

Version 2 adoption is explicit. Keep legacy graphs usable without silently
inventing identities on read or during indexing. For migration, preview with
the reviewed graph UUID, origin UUID, and a local Git ancestor. A shared graph
namespace identifies the same project; independent branch additions need
distinct origins. Branch-local nodes are full authored nodes, usable before
commit, not a separate reduced-function draft namespace.

Migration examines history and may require explicit continuity decisions.
Restore-ancestor versus new-identity choices need the exact review hash and a
reason. Unknown, shallow, ambiguous, or incomplete ancestry must not be repaired
by guessing. Historical prose and immutable external evidence are not rewritten
merely because today's numeric alias changes.

### Reviewed reconciliation

1. Preserve the target checkout's staged and unstaged work. Establish the exact
   local ancestor, incoming commit, and current target HEAD.
2. Preview `mdkg graph reconcile` with those refs. Read the identity mapping,
   changed paths, conflicts, and evidence before applying anything.
3. Different identities sharing an alias are not two edits of one node: keep
   target aliases and review deterministic incoming remaps and reference binds.
   Same-identity conflicting edits, evidence/lifecycle changes, deletion, and
   reintroduction need explicit choices rather than duplicate-ID repair.
4. Supply reasoned decisions, preview again, and apply only the resulting exact
   unchanged plan hash. Repeated integration must use recorded target acceptance,
   not trust an imported receipt merely because its self-hash verifies.
5. Validate graph identities/references and review the authored diff. Under
   separate Git authority, commit that exact reviewed graph result on the target
   before starting the native ancestry-preserving merge of the pinned incoming
   revision. Resolve graph paths to that reviewed result, source/configuration
   changes separately, then validate the combined source-plus-graph tree before
   committing the merge. Never apply blanket `ours` treatment to `.mdkg`.
6. Verify both parent ancestries and repeated integration. Reconciliation itself
   does not stage files, switch branches, merge Git history, fetch, or push.

Use native `git worktree` for separate developer checkouts, one writer per
checkout. Related worktrees retain the same graph identity while independent
node creation receives distinct identities. Indexes, selection, transient locks,
journals and live DB state stay checkout-local; do not merge them as project
knowledge. Durable goal claims still change shared graph lifecycle, not distributed
execution leases. Ordinary worktree success does not qualify submodule/gitdir
indirection; final tests cover those separately. This is the required integration
protocol, not a claim that its final0.6.0 platform matrix already passed.

Clone preserves same-project identity. An independent fork creates new graph
and node identities with lineage mappings. Neither transfers live writer locks,
local selection, or runtime ownership. Parent graphs may inspect authorized
child snapshots; they do not acquire child write authority or a promise that
the snapshot reflects the child's current working tree.

## Accepted compatibility boundaries and remaining proof

The following policies are accepted; local remedies still require final-artifact
and independent qualification. Historical investigations are not repeated gates.

| Gate | Observed condition | Accepted treatment and remaining proof |
| --- | --- | --- |
| Old writers on v2 | Published 0.5.2 can partially write; old initialization can bypass configuration fencing | Upgrade every writer before adoption; the reviewed schema2 fence is implemented, old init limits remain explicit |
| Killed writer | Abrupt termination can leave a mutation lock | Implemented explicit lock/journal/file-bound recovery; local three-runtime SIGKILL proof is intermediate, final platform proof remains |
| Legacy public bundles | Policy-less snapshots cannot prove configured runtime exclusions | Bounded inspection remains; fresh policy-bound safe export is required before mutation consumers accept it |
| Observational Git reads | Older helpers refreshed parent/child Git index metadata or could invoke configured helpers | Shared observational helpers now suppress optional writes and refuse unreviewed filters; final installed/read-only/platform coverage remains |
| Historical migration | Historical alias-shaped evidence may lack unambiguous stable identity | Preserve exact unsupported-condition proof; do not invent identities or rewrite history to pass |

For a supported caught-error transaction, `mdkg graph recover` can inspect the
journal before a reviewed resume or rollback. Caught-error evidence alone does
not qualify abrupt termination; use the explicit ownership procedure below.
Do not manually delete an
unexamined lock, weaken custody checks, or restore a whole checkout to bypass it.

### Explicit compatible-writer fence (candidate, Task 835)

Legacy initialization and ordinary configuration reads remain schema 1. Reviewed
v2 migration installs configuration schema 2 as its first authored operation,
binds exact before/after bytes in the plan and journal, and restores the original
configuration last on rollback. Identities are still governed by `.mdkg/graph.json`;
the configuration fence is not an alternative identity authority.

For an already-adopted pre-release v2 graph with schema 1 configuration, preview
`mdkg upgrade --only .mdkg/config.json --json`, then apply only its exact reviewed
plan. This preserves existing identities and authored settings; reads do not
silently upgrade the configuration. Unfenced historical migration journals remain
inspectable and eligible for exact rollback, not automatically approved for resume.

This stops ordinary published 0.5.2 writers that honor configuration versions;
it cannot control an old executable's `init` or `init --force`. Upgrade every
writer before adoption and never mix unsupported clients. The current candidate
also refuses unsupported graph/config capabilities at affected event, cache,
SQLite and explicit report-output write boundaries. Console-only validation
diagnostics remain observational. These controls are not a writer lease, external
attestation, or proof that killed-writer recovery is complete.

### Explicit interrupted-writer recovery (candidate, Task 836)

Inspect with `mdkg graph recover <plan-hash> --json`. For a proven orphan, review
the requested mode's `recovery.resume` or `recovery.rollback` result, then pass
its exact `lock_evidence` value with `--resume` or `--rollback` and
`--lock-evidence <sha256>`. This is an explicit recovery approval, not a lease,
automatic cleanup, Git operation, or permission to change unrelated files.

New graph transactions record checkout-specific lock epochs. Recovery binds the
issued directory, complete owner/claim chain, exact journal bytes/inventory,
current authored/control/dependency bytes, and local boot/user/namespace proof.
All recorded owner processes must be absent in that same environment. A live,
suspended or reused PID, foreign checkout/boot, restricted OS proof, weak old
owner, incomplete claim or unknown journal/lock file refuses without guessing.
A complete rollback claim remains irreversible if its writer dies before the
journal is updated. Do not manually erase evidence to bypass a refusal.

Supported qualification boundaries are complete published owner+journal,
claim and operation states, including a terminal journal whose lock remains.
Partial metadata, journal temporary residue and partial lock cleanup remain
insufficient-evidence refusals. This does not claim recovery from every possible
power-loss instruction window or fencing against malicious same-user pathname
races. Final macOS/Linux artifact qualification and independent security review
remain required; source or intermediate-package proof is not release clearance.

## Breaking-change conversion checklist

No conversion below happens silently during init or upgrade. Preserve user files,
historical receipts and unrelated custom fields; review each authored change.

| Previous surface | 0.6.0 treatment |
| --- | --- |
| `mdkg git clone/fetch/push/materialize/closeout/push-ready` | Removed completely. Use native Git under separately reviewed auth, trust, source acceptance and commit/push policy. Retain observational `git inspect`. |
| `validate --profile`, `work validate --profile`, built-in `omni-room` validation | Removed, no fallback. Generic field/reference checks remain; consumers interpret opaque contract/policy references. |
| `room_orchestrated` runtime mode | Replace deliberately with generic `orchestrated`; the old enum token is invalid, not an alias. |
| First-class `--pricing-model`, mandatory/default pricing metadata | Removed from CLI/generated templates. Keep economics outside mdkg; existing unknown fields receive ordinary custom-template handling, not special compatibility. |
| Special `ochatr_` skill extraction, weighting, rendering and JSON projection | Removed. Source custom fields are not rewritten; there is no privileged namespace or replacement metadata framework. |
| `init --llm/--agents/--claude/--omni` | Still unsupported, not newly removed from 0.5.2. Use default compact init, compatible `--agent`, or explicit `--graph-only`. |

Removed commands/options fail ordinary admission before config discovery or
effects. That does not prohibit an independently useful generic flag on its own
supported command. Do not substitute a new hidden Git wrapper or pretend that a
generic profile label executes the removed consumer policy.

## Derived state, workspace ownership and evidence

JSON and SQLite caches are derived access paths, never identity authority.
Copied, stale or unbound caches do not prove freshness; normal reads derive
current authored metadata without writes. Explicit stale-cache opt-out warns.
Malformed-cache diagnostics remain. Content fingerprints are neither immutable
node identities nor authenticity signatures. Explicit indexing or archive
compression is a separately authorized write, not an observational side effect.

`validate --changed-only` filters warning paths, including literal POSIX names
and nested checkouts; errors still apply to the complete graph. Do not use it
as a substitute for full release validation or infer Windows qualification.

Parent-owned workspaces and independently executed root graphs are different
ownership models. Default compact init creates root-scoped event history;
subsequently re-aliasing that history as a parent workspace can fail validation.
Explicit graph-only setup preserves the parent-workspace fixture contract, but
does not authorize rewriting an independently executed child's events. Final
test477 must disposition this observation; this document is not a waiver.
Read-only subgraph snapshots remain a separate transport path.

Receipt verification checks structure, local references and recorded evidence
hashes. It does not authenticate external execution, payment or attestations.
Full operational receipts, accounting, reputation, scheduling, and provider
state remain consumer-owned. mdkg carries distilled intent, portable contracts,
accepted project evidence and explicit references. This release does not add
federation, remote skill distribution, or autonomous self-improvement.

## Final qualification and publication handoff

Before accepting a final release candidate:

1. Recheck all blocker dispositions, remaining compatibility observations and
   exact dirty/source custody. Existing local proof is not final artifact proof.
2. Freeze the0.6.0 package inputs and create one candidate tarball. Keep the
   public release manifest `draft`, never `published` in this local-only pass.
   Generate/verify release references and use these same bytes for qualification.
3. Complete a fresh full Standard security workflow, then independently review
   the complete remediation range, including deleted/supporting code. Preserve
   canonical scan reports in their designated private location; commit sanitized
   findings, dispositions and report hashes only.
4. Run all six installed fixture families on macOS and Linux x86_64/ARM64 across
   Node24.15.0, the recorded supported24 runtime and Node26. Distinguish native
   and emulated execution; never count unavailable executors as passes. Include
   actual read-only mounts, legacy/v2, JSON/SQLite, private migration rehearsal,
   independent branches, mixed staged/unstaged state, recovery, scale and goals.
   A known refusal can be accepted only against an explicit agreed contract.
5. Run the full release ladder with coverage floors unchanged: 89% lines,
   77% branches, 96% functions. Verify CLI/docs/skills/package contents, graph
   full/changed-only checks, SQLite, diff review, and protected-state bookends.
6. Seal one tarball with its integrity, file manifest, package-input hashes,
   source revision, runtimes, audit reports and validation receipts. Package-input
   changes invalidate the seal. Evidence-only commits may follow without changing
   the sealed package bytes.
7. Leave publication paused. A future authorized publication pass must recheck
   blockers and consume the exact qualified artifact. A green goal status alone
   is not publication evidence or authority. Push, tag, release and provider
   actions retain their separate authority boundaries.

Until those gates close, report **NOT_READY**, not “ready except for publishing.”
